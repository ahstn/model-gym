## 5. Label rubric

The input contract remains command-visible operational risk. Only command text will be a model feature. Reviewer metadata, reasons, source URLs, groups, and labels must never be inserted into the command or supplied as model features.

Dialect metadata can explain syntax, but it must not justify contradictory labels for identical command-only inputs. If the label depends on an otherwise hidden interpreter or platform, use a naturally explicit interpreter invocation where appropriate, or quarantine the case. Do not hide information needed to infer the label in the provenance sidecar.

Use the existing five-level taxonomy:

| Level | Slug | Meaning | Reference action |
| 1 | critical | Potentially catastrophic or irreversible; broad production or data destruction. | block |
| 2 | dangerous | Destructive or access-impacting with significant blast radius; usually recoverable. | approve |
| 3 | high_risk | Can destroy local state, interrupt services, or cause meaningful operational damage. | approve |
| 4 | caution | Potentially disruptive or security-weakening, but not normally destructive by itself. | flag |
| 5 | low_risk | Normally non-destructive or read-only. | allow |

These reference actions describe gold severity bands, not the current probability-threshold policy. Do not use a trained model's predictions, a DCG verdict, or a regex score as ground truth.

For each row, identify:
1. The operation that actually executes, including wrappers and inline code.
2. Its visible target and scope: one resource versus recursive, wildcard, all, namespace, account, or filesystem-wide effects.
3. Data loss, service interruption, privilege changes, disclosure, and other supported effects.
4. What recovery or safeguards the documented command actually provides.
5. Which flags change effects and which merely suppress confirmation or errors.
6. What remains unknown from command text alone.

Assign the most severe supported effect, not the worst imaginable hidden scenario. State potential consequences conditionally when their prerequisites are unknown. Do not invent an active production account, the only backup, a sole administrator, compromised credentials, or downstream consumers to justify a label.

Conversely, localhost, /tmp, an opaque ID, a name containing dev/test, or a filename ending .example does not prove that data is disposable or contains no secrets. Known destructive semantics still matter. Do not make prod/dev naming a universal labeling rule.

Read-only does not automatically mean low risk: printing credential values, creating a public share, changing visibility, or uploading sensitive content needs separate review. Metadata-only inspection and public-key inspection are useful safe counterparts. Distinguish benign network activity from disclosure supported by the visible payload and destination. Do not copy DCG's private-address allowlists or unconditional tool exemptions into our risk labels.

A real dry-run/preview changes only the operations it actually suppresses. --force, --yes, --quiet, --no-prompt, and --auto-approve are not dry runs. A preview flag does not neutralize an earlier substitution, redirection, another command in a chain, or an invoked program outside its scope. EXPLAIN ANALYZE is not generally the same as EXPLAIN.

Do not automatically label invalid syntax as safe. Exclude malformed examples from ordinary training and put them in a separate diagnostic set. An invalid outer operation may still follow a harmful shell expansion or redirection. Do not label every mutation or every command containing sudo, delete, secret, or production as critical.

If choosing between two levels requires unavailable context, or conflicts with a credible existing annotation, obtain independent adjudication. Quarantine unresolved cases. Do not silently modify old labels, treat old rationales as infallible, or add a sixth class to accepted training data. Log suspected legacy-label issues separately.

## 6. Positive, negative, and contrast balance

Target 20% per level overall, within two percentage points; within each split, allow five points to preserve groups. Do not relabel rows to hit balance. Here hazardous positives mean levels 1-3, low-risk negatives mean level 5, and level 4 is a separate caution boundary, not an interchangeable negative class.

Require these overlapping coverage slices:
- At least 4,000 rows in reviewed contrast sets of 2-6 cases. Change one meaningful factor when possible, and state the expected semantic difference. Include level-1/2, 2/3, 3/4, and 4/5 boundaries, not only catastrophic versus trivial.
- At least 1,000 genuinely low-risk hard negatives: destructive words used as inert data; metadata/status/help/inspection operations; supported previews; narrow read-only queries; public material rather than secret contents.
- At least 1,000 composition or wrapper cases: command chains, substitutions, pipelines, redirections, remote commands, inline interpreters, or PowerShell/Cmd execution contexts. Include both safe and unsafe outcomes.
- At least 500 reviewed invariance pairs: documented alternate spellings, flag order, equivalent quoting, or a wrapper that truly preserves the effect. Keep both rows in the same group. Do not infer equivalence from visual similarity.

Examples of distinctions to research, not automatic gold labels:
- Quoted destructive text passed to printf/grep versus executed by sh -c or a command substitution.
- Git inspection versus reset/clean/history rewrite, checked versus forced deletion, and local versus shared effects.
- SQL filtered writes versus full-table operations, and secret values versus secret metadata.
- Storage copy versus synchronization that removes destination objects; backup creation versus recovery-point removal.
- Download versus upload, routine API reads versus state-changing endpoints, and inert payload text versus execution.
- PowerShell -WhatIf only on commands that honor it; native Cmd flags and PowerShell parameters must not be mixed.
- Case-sensitive flags such as git branch -d/-D. A semantic change need not always cross a risk-level boundary.

Spread each tool across safe and risky examples. Include safe operations on production-named resources and risky operations on development-named resources where justified. Use realistic neutral identifiers too. Do not pad with renamed buckets, changed UUIDs, comments, extra whitespace, repeated prompts, or label-bearing words such as safe_example and dangerous_target.

## 7. Evidence, records, and compatibility

Every accepted row needs these existing semantic fields:
command, level, label, category, group, shell, reason, source.

- level is an integer 1-5; label is the matching slug.
- command contains only the exact command text, never a rationale or risk annotation. Preserve case, quotes, backslashes, Unicode, operators, and significant whitespace. JSON-escape newlines without replacing their meaning.
- reason is a short causal explanation of operation, scope, consequences, safeguards, and uncertainty. No unsupported environment facts or claims of inevitability.
- source must truthfully mark generated/documentation-adapted content, for example synthetic:docs-grounded-v2. Do not call generated content production traffic or human-reviewed data.
- group is explicitly assigned. Do not use the fallback leading-program heuristic for this release.

Create a provenance sidecar with a stable exact-text hash and shell, plus: primary and secondary pack IDs; tool and documented version; exact supporting URL(s) and section; access date or pinned revision; evidence supporting the syntax and effects; origin kind; transformation from a source scenario; contrast/invariance links; initial and blind-review labels; reviewer type/identifier; adjudication; confidence; and final disposition. A shared verified source can support a family, but every row must link to the evidence for its own flags and effects. A generic homepage is insufficient.

Use current category values where they fit. For missing domains, propose precise additive categories in a machine-readable schema manifest; do not funnel Kafka, payments, and all new tools into shell. Likewise, current shell values are bash/sql/redis/http/powershell; native Cmd needs an explicit cmd extension rather than a false bash label. SQL submitted through a shell client has the outer shell dialect; native SQL has sql. Preserve this distinction.

Important: current RiskRecord normalizes ALL whitespace, including whitespace inside literals and multiline scripts. Do not round-trip loss-sensitive examples through it. Keep a lossless staging schema, exact hashes, and a compatibility report. Reuse the existing ID/validation helpers for compatible rows; detect normalization collisions and semantic changes. For unsupported or loss-sensitive rows, use the lossless staging contract and a distinct exact-text key, clearly identify required ingestion changes, and never claim legacy-loader parity. Do not rewrite commands merely to hide the incompatibility. Keep all source and model code unchanged in this task.

Check original and proposed commands for syntactic and semantic validity using primary tool documentation. First produce a 300-row pilot drawn from the intended training split. Include multiple domains, all five levels, hard negatives, and boundary pairs. Validate schema, evidence, group quality, and labels before scaling. The pilot counts toward the 8,000 training target only if accepted.

Every candidate gets a second, blind label pass. Give that reviewer the command, explicit dialect/platform assumptions, rubric, and source evidence, but not the first label or rationale. Independent reviewers may be agents, but describe them honestly as model reviewers; do not claim human adjudication or statistical independence just because sessions differ. If delegating, partition ownership by tool families and source scenarios. Workers write separate shards and skip global validation. Never use automatic scope.level + variant.shift rules as the final labeler. Generation helpers may instantiate valid syntax; each accepted case still needs a reviewed label and a checked explanation of the variant's actual effect.
